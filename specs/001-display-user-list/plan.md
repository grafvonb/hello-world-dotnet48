# Implementation Plan: Display Users in the Main Window

**Branch**: `001-display-user-list` | **Date**: 2026-11-02 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `specs/001-display-user-list/spec.md`

## Summary

Replace the greeting demonstration with a read-only Name/Login/Age list that loads on launch.
Reuse `IUserService.GetAllAsync` and the configured `SqlUserService`; preserve source ordering.
Keep the existing XAML and code-behind structure. A bounded DataGrid and a single guarded async
load flow provide populated, loading, empty, and failed states with Retry. Closing requests
cancellation and prevents any later UI update. Database setup and writes remain outside this view.

## Technical Context

**Language/Version**: C# 7.3, XAML, .NET Framework 4.8; Windows PowerShell 5.1 for validation.

**Primary Dependencies**: Existing WPF assemblies, System.Configuration, UserDatabaseService;
add a built-in System.Data reference to the desktop project for typed SqlException handling.
No new packages, application projects, or service framework.

**Storage**: Existing SQL Server `dbo.[User]`, accessed only through the existing service.
No schema changes, migrations, seeding, or setup during application startup.

**Testing**: Visual Studio MSBuild; a dependency-free STA window harness in
`scripts/Test-MainWindow.ps1` using a controllable fake IUserService; keyboard/manual checks;
an isolated real SQL smoke check. Existing service integration script is required only if
service/schema code changes, which this design does not require.

**Target Platform**: Windows desktop with the installed .NET Framework runtime capable of
running net48; Visual Studio MSBuild and .NET Framework 4.8 reference assemblies for builds.

**Project Type**: Desktop application plus existing data-service library.

**Performance Goals**: Loading feedback within one second; display a supplied result of up to
1,000 records within one second; window remains movable and closable during pending I/O.

**Constraints**: Preserve the classic project format, language/framework targets, configured
connection, source ordering, and existing data invariants. No UI-thread blocking waits, direct
SQL in the application, or exception/connection detail disclosure.

**Scale/Scope**: One window, all returned users, acceptance collections of 1/100/1,000 users.
No pagination, filtering, CRUD UI, new authentication, or refresh after successful loading.

### Phase 1: Design

- Constructor initializes controls without resolving configuration or opening storage.
  Retain a public parameterless constructor for StartupUri. Add
  `MainWindow(Func<IUserService> serviceFactory)` as a small test seam; the default factory
  reads configuration and constructs the service only inside the guarded loading flow.
- Loaded invokes the shared Task-returning load method once, guarded against repeated Loaded
  events. Retry invokes the same method only from failure. Event handlers are thin async-void
  adapters; all operational failures are caught within the awaited loading flow.
- Set loading state and the in-flight flag before the first await. Show feedback before
  starting source work; yield to the Dispatcher if necessary so a fast synchronous outcome
  cannot prevent initial rendering. Await service I/O directly on the captured UI context.
- Bind the completed IReadOnlyList<User> once. Choose populated or empty by Count; do not trim,
  deduplicate, or re-sort records. Disable user column sorting to retain the scoped order.
- Use a resizable Window and a Grid with a star-sized DataGrid row. Explicit Name/Login/Age
  columns, read-only interaction, no add/delete rows, native scrolling, row virtualization,
  and keyboard access preserve usability for 1,000 rows and 100-character fields.
- Resolve configuration/service construction inside the load try block. Detect missing/blank
  UserDatabase settings and invalid connection values as configuration failures. Map typed SQL
  failures to safe connection/access/storage categories; use a generic load-failure fallback.
  Do not expose raw exception messages or claim a specific cause when SQL reports ambiguity.
- Closed is terminal: mark closed, request cancellation, and skip all post-await/catch/finally
  UI mutations after closure. Suppress close-related cancellation; never wait for I/O to close.
  Dispose the CancellationTokenSource after closure once active work settles, or immediately on closure if none is active.
- [data-model.md](data-model.md) defines the data and state model.
  [contracts/main-window.md](contracts/main-window.md) and
  [contracts/user-source.md](contracts/user-source.md) define the observable interfaces.

### Validation design and handoff

Implement a bounded STA harness using Add-Type and the existing application/service assemblies.
A factory can return a controllable fake or throw before a service exists. Drive Loaded and Retry
through real window events/controls; assert visible states, row values/count, no overlapping calls,
retry recovery, and close behavior. Every fake setup/write method records and fails unexpected use.
Use bounded Dispatcher pumping instead of blocking the UI thread. Test a provider that honors
cancellation and one that completes after close. Use native keyboard checks for long text and
first/last rows, and record timings for the specified acceptance collections.

[quickstart.md](quickstart.md) provides build/run commands and acceptance cases. It distinguishes
planned commands from existing ones, SQL fixture preparation from application behavior, and
automated checks from manual checks. Update README during implementation. No application build,
UI execution, or database mutation is performed by this documentation-only planning command.
